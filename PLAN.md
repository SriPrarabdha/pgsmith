pg_flagsmith — Flagsmith flags inside Postgres
Nov 23, 2026 · @Prarabdha Srivastava
Summary
pg_flagsmith evaluates Flagsmith feature flags inside Postgres, returning exactly what Flagsmith's official engine returns for the same input. It ships as a Trusted Language Extension, so it installs on Supabase and Amazon RDS with no compiled code.
Goals
• Parity: the same enabled state, value, variant and reason as the official engine, proven against Flagsmith's engine-test-data suite and checked live against your own instance.
• Installs anywhere: pure SQL and PL/pgSQL, packaged for pg_tle and installable from database.dev.
• Atomic: a configuration change is either fully visible to a statement or not at all.
• Fast: set-based evaluation over millions of rows, with configuration compiled into SQL the planner can inline.
Non-goals
• Editing flags. Flagsmith stays the source of truth; Postgres holds a read-only replica of the configuration.
• Recording experiment exposures inside a SELECT. Writes from reads break on replicas and surprise people; exposures go through a queue table (stretch goal).
• Flag-dependency conditions ($.flags.<name>.enabled). Ship them only if the conformance suite includes them and time allows.

System architecture
Flagsmith's document flows down through one transaction into immutable snapshot tables; your SQL reads them through the interpreter or the compiled functions, and the SDK still sends experiment events straight to Flagsmith.
The engine contract
Parity means one thing: for the same input, pg_flagsmith returns what the official engine's get_evaluation_result(context) returns. The canonical input is the engine's EvaluationContext JSON, the same format as every engine-test-data test case, so one loader serves both the test suite and production.
The Python engine is the reference, because the test corpus was generated by running it (test data PR). The Rust port is the most readable spec of the logic (engine.rs, segment_evaluator.rs), but where the two differ, Python wins.

The hash that drives every split and variant, with ids joined by commas:
p = \frac{\operatorname{int}(\operatorname{md5}(\text{ids})) \bmod 9999}{9998} \times 100
If p comes out at exactly 100, the engine hashes again with the ids repeated (Ruby SDK). That happens for 1 in 9,999 inputs, so it needs its own test.
Known divergences to pin with tests
• REGEX: Python uses re.match, which anchors at the start of the value (PR #8840); the Rust port searches anywhere. Follow Python.
• MODULO: Python's % on floats takes the sign of the divisor; Rust's takes the sign of the dividend. They differ for negative traits. Follow Python.
• Hash collision: a split and a variant collide when a segment key equals a feature key (issue #348). Replicate it; parity includes the bugs.
Table schema
Every configuration lives in an immutable, numbered snapshot; serving a new configuration means flipping one pointer. Each child table is keyed by snapshot_id first, so one snapshot's rows sit together in every index and every query pins exactly one snapshot.
CREATE SCHEMA flagsmith;     -- extension objects
CREATE SCHEMA flagsmith_c;   -- generated per-snapshot functions (compiled path)

CREATE TYPE flagsmith.rule_type AS ENUM ('ALL', 'ANY', 'NONE');
CREATE TYPE flagsmith.semver AS (major numeric, minor numeric, patch numeric, pre text[], build text);
CREATE TYPE flagsmith.flag_result AS (
  feature text, enabled boolean, value jsonb, variant text, reason text);

-- One row per Flagsmith environment mirrored into this database
CREATE TABLE flagsmith.environment (
  env_key          text PRIMARY KEY,
  name             text NOT NULL,
  current_snapshot bigint,                      -- the single pointer that a load flips
  regex_policy     text NOT NULL DEFAULT 'reject'
                   CHECK (regex_policy IN ('reject', 'false', 'approximate')),
  compile          boolean NOT NULL DEFAULT true,
  keep_snapshots   int NOT NULL DEFAULT 50 CHECK (keep_snapshots >= 2)
);

-- Immutable configuration versions; 'candidate' snapshots are never served
CREATE TABLE flagsmith.snapshot (
  snapshot_id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  env_key        text NOT NULL REFERENCES flagsmith.environment ON DELETE CASCADE,
  kind           text NOT NULL DEFAULT 'live' CHECK (kind IN ('live', 'candidate', 'test')),
  content_sha256 bytea NOT NULL,
  context        json NOT NULL,     -- json, not jsonb: segment key order decides tie-breaks
  source         text NOT NULL,     -- 'pusher' | 'pg_net' | 'manual' | 'flagshift'
  source_rev     text,              -- Flagsmith ETag or updated_at, for idempotent loads
  loaded_at      timestamptz NOT NULL DEFAULT now(),
  compiled_fn    regprocedure,      -- NULL when compiling is off or failed
  UNIQUE (env_key, kind, content_sha256)
);
ALTER TABLE flagsmith.environment ADD FOREIGN KEY (current_snapshot)
  REFERENCES flagsmith.snapshot DEFERRABLE INITIALLY DEFERRED;

CREATE TABLE flagsmith.segment (
  snapshot_id bigint REFERENCES flagsmith.snapshot ON DELETE CASCADE,
  seg_ord     int,                  -- position in the context's segments object
  segment_key text NOT NULL,        -- hashed by PERCENTAGE_SPLIT
  name        text NOT NULL,
  source      text NOT NULL DEFAULT 'api' CHECK (source IN ('api', 'identity_override')),
  metadata    jsonb,
  PRIMARY KEY (snapshot_id, seg_ord)
);

CREATE TABLE flagsmith.rule (
  snapshot_id bigint,
  rule_id     int,                  -- preorder id within the snapshot
  seg_ord     int NOT NULL,
  parent_id   int,                  -- NULL = a top-level rule of the segment
  ord         int NOT NULL,         -- position among siblings
  rule_type   flagsmith.rule_type NOT NULL,
  PRIMARY KEY (snapshot_id, rule_id),
  FOREIGN KEY (snapshot_id, seg_ord) REFERENCES flagsmith.segment ON DELETE CASCADE,
  FOREIGN KEY (snapshot_id, parent_id) REFERENCES flagsmith.rule
);
CREATE INDEX ON flagsmith.rule (snapshot_id, seg_ord, parent_id, ord);

-- Condition values are parsed once at load; the reference engine re-parses per call
CREATE TABLE flagsmith.condition (
  snapshot_id bigint,
  rule_id     int,
  ord         int,
  property    text NOT NULL,        -- '' when absent
  operator    text NOT NULL,        -- text, not an enum: unknown operators must load and evaluate false
  value_raw   json,                 -- string or array, exactly as given
  prop_kind   text NOT NULL,        -- 'trait' | 'identifier' | 'identity_key' | 'env_key' | 'env_name'
                                    -- | 'jsonpath' | 'flag' | 'none'
  prop_trait  text,                 -- trait name when prop_kind = 'trait'
  v_text      text,
  v_list      text[],               -- IN, split and trimmed
  v_bool      boolean,              -- 'true' / 'false' / '1'
  v_int       numeric,              -- integer parse; numeric, so big values behave like Python's int
  v_float     float8,
  v_semver    flagsmith.semver,     -- when the value ends in ':semver'
  v_regex     text,                 -- rewritten for Postgres, anchored at the start
  v_mod_div   float8,
  v_mod_rem   float8,
  v_threshold float8,               -- PERCENTAGE_SPLIT
  status      text NOT NULL DEFAULT 'ok'
              CHECK (status IN ('ok', 'unsupported', 'unknown_operator')),
  PRIMARY KEY (snapshot_id, rule_id, ord),
  FOREIGN KEY (snapshot_id, rule_id) REFERENCES flagsmith.rule ON DELETE CASCADE
);

-- Environment defaults (seg_ord NULL) and segment overrides share one shape
CREATE TABLE flagsmith.feature_context (
  fc_id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  snapshot_id  bigint NOT NULL REFERENCES flagsmith.snapshot ON DELETE CASCADE,
  feature_name text NOT NULL,
  seg_ord      int,               -- NULL = environment default
  feature_key  text NOT NULL,     -- multivariate hashing salt
  enabled      boolean NOT NULL,
  value        jsonb,
  priority     float8 NOT NULL DEFAULT 'Infinity',  -- '-Infinity' for identity overrides
  win_rank     int,               -- test order for this feature's overrides: (priority, seg_ord)
  metadata     jsonb,
  FOREIGN KEY (snapshot_id, seg_ord) REFERENCES flagsmith.segment ON DELETE CASCADE
);
CREATE UNIQUE INDEX ON flagsmith.feature_context (snapshot_id, feature_name) WHERE seg_ord IS NULL;
CREATE INDEX ON flagsmith.feature_context (snapshot_id, feature_name, win_rank) WHERE seg_ord IS NOT NULL;

CREATE TABLE flagsmith.variant (
  fc_id       bigint REFERENCES flagsmith.feature_context ON DELETE CASCADE,
  ord         int,                -- after a stable sort by priority
  value       jsonb,
  variant_key text,               -- NULL when the option has no key
  weight      float8 NOT NULL,
  cumulative  float8 NOT NULL,    -- running float8 sum in ord order
  PRIMARY KEY (fc_id, ord)
);

-- Identity overrides: an indexed lookup instead of scanning an IN list
CREATE TABLE flagsmith.identity_override (
  snapshot_id bigint,
  identifier  text,
  seg_ord     int NOT NULL,       -- the synthetic segment holding this identity's overrides
  PRIMARY KEY (snapshot_id, identifier),
  FOREIGN KEY (snapshot_id, seg_ord) REFERENCES flagsmith.segment ON DELETE CASCADE
);

CREATE TABLE flagsmith.snapshot_warning (
  snapshot_id bigint REFERENCES flagsmith.snapshot ON DELETE CASCADE,
  severity    text NOT NULL CHECK (severity IN ('error', 'warning')),
  code        text NOT NULL,      -- 'regex_unportable' | 'jsonpath_unsupported' | 'unknown_operator' | 'flag_dependency'

Design notes
• Immutable rows. The loader writes a snapshot once and nothing updates it; garbage collection deletes whole snapshots through the cascades.
• Parse once. The v_* columns move every condition-value parse to load time. At evaluation, only the trait side is parsed.
• Fail loudly on broken assumptions. The identity_override primary key encodes the SDK mapper's rule that each identifier sits in one override group. A violation fails the load instead of guessing.
• Unknown operators load. SDKs evaluate an unrecognised operator as false (operator docs), so the loader keeps the row, marks it unknown_operator and logs a warning.
Hashing, splits and multivariate allocation
Hashing is the only expensive step per row, so the design computes each MD5 once per (salt, key) pair and reduces the 128-bit digest mod 9999 in bigint arithmetic. No numeric type, no extension, no compiled code.
Reducing a 128-bit digest mod 9999. Split the 32-hex-digit digest into four 32-bit words and fold them left to right. The largest intermediate value is 9,998 × 2³² + 2³², about 4.3 × 10¹³, far inside bigint.
r_0 = 0, \qquad r_{i} = (r_{i-1} \cdot 2^{32} + w_i) \bmod 9999, \qquad r = r_4
CREATE FUNCTION flagsmith.md5_mod9999(h text) RETURNS int
LANGUAGE plpgsql IMMUTABLE STRICT PARALLEL SAFE AS $$
DECLARE r bigint := 0;
BEGIN
  FOR i IN 0..3 LOOP
    r := (r * 4294967296
          + ('x' || lpad(substr(h, i * 8 + 1, 8), 16, '0'))::bit(64)::bigint) % 9999;
  END LOOP;
  RETURN r;
END $$;

-- The engine's hashed percentage, including its rehash when the result is exactly 100
CREATE FUNCTION flagsmith.hash_pct(ids text[]) RETURNS float8
LANGUAGE plpgsql IMMUTABLE STRICT PARALLEL SAFE AS $$
DECLARE
  rep text[] := ids;
  r   int;
BEGIN
  LOOP
    r := flagsmith.md5_mod9999(md5(convert_to(array_to_string(rep, ','), 'UTF8')));
    EXIT WHEN r <> 9998;          -- 9998 / 9998 × 100 = 100 → hash again
    rep := rep || ids;            -- Python repeats the list: a,b,a,b
  END LOOP;
  RETURN r::float8 / 9998 * 100;  -- same operation order as the reference
END $$;
Three details carry the parity:
• Bytes, not text. convert_to(…, 'UTF8') hashes UTF-8 bytes whatever the database encoding, matching the SDKs.
• Repeat the list, not the string. Python repeats the id list and joins once (a,b,a,b). An older Rust version appended the joined string without a separator (a,ba,b). Follow Python.
• Same float operations. r / 9998 × 100 in float8, in that order, gives bit-identical results to Python's float arithmetic.
Percentage split. The condition is one comparison, inclusive at the boundary:
flagsmith.hash_pct(ARRAY[segment_key, split_key]) <= v_threshold
-- split_key = the identity key, or the property's value when the condition names one
The boundary case is real. A digest that reduces to 4,999 gives 4,999 / 9,998 × 100 = 50.0 exactly, which a 50% split must include.
Multivariate allocation. The loader stable-sorts variants by priority and stores a running float8 sum, so evaluation is a single ordered probe:
-- p is computed once, before the probe
SELECT v.value, v.variant_key, v.weight
FROM flagsmith.variant v
WHERE v.fc_id = $1 AND v.cumulative >= $2   -- $2 = hash_pct(ARRAY[feature_key, identity_key])
ORDER BY v.ord
LIMIT 1;                                    -- no row → the control value, variant 'control'
Variant selection runs only when the feature has variants, an identity is present and the feature key is non-empty; otherwise the plain value is served.
Speed path. The PL/pgSQL call costs a few microseconds per hash. For self-managed Postgres, an optional native companion (Rust, pgrx) can replace hash_pct with the same signature; the same conformance suite gates it. The TLE build stays pure.
Operators
Every operator follows one rule: the condition side is parsed once at load, the trait side is classified by its JSON type at evaluation, and anything missing or unparseable is false, never NULL.
Classifying the trait. jsonb_typeof gives boolean, string or number. A number is an integer when its text has no ., e or E, otherwise a float. A JSON null counts as not set. Integers compare as numeric, so large values behave like Python's unbounded int.

REGEX rewriting. Python's re.match(p, s) becomes s ~ '^(?:p)' in Postgres, with three adjustments:
• Inline flags. Postgres accepts embedded options only at the very start, so a leading (?i) is hoisted in front of the anchor.
• Newlines. Python's . does not match a newline by default; Postgres's does. Prefixing the (?p) option makes . skip newlines while ^ still anchors at the start of the string.
• Python-only syntax. Named groups (?P<n>…), atomic groups and possessive quantifiers have no Postgres equivalent. The loader marks those conditions unsupported and applies the environment's regex_policy: reject keeps the previous snapshot and raises an alert, false evaluates them as false, approximate evaluates anyway and logs a warning.
Flagsmith's own SQL translator treats some regex patterns the same way: it returns nothing for patterns a dialect cannot compile and asks the caller to fall back (flagsmith-sql-flag-engine).
SemVer precedence. semver_cmp implements the SemVer 2.0 order: major, minor and patch numerically; a release outranks any pre-release of it; pre-release identifiers compare pairwise, numbers numerically and below text, text by ASCII; a shorter identifier list ranks lower when it is a prefix. The test vector is the spec's own chain: 1.0.0-alpha < 1.0.0-alpha.1 < 1.0.0-alpha.beta < 1.0.0-beta < 1.0.0-beta.2 < 1.0.0-beta.11 < 1.0.0-rc.1 < 1.0.0. Flagsmith's SQL translator compares only major.minor.patch and ignores pre-releases, so this goes beyond it. Whether build metadata breaks ties is a reference-engine detail to confirm against the suite.

Overrides
Precedence is fixed: an identity override beats every segment override, the lowest-numbered segment override beats the rest, and the environment default comes last. The loader turns that rule into one precomputed rank per override, so evaluation is a single ordered lookup.
Segment override priority. The reference walks matching segments in context order and replaces the current winner only when a candidate's priority is strictly lower. That always lands on the lowest priority, and among equal priorities, the segment seen first. So sorting each feature's overrides by (priority, seg_ord) once gives the same answer:
-- at load
UPDATE flagsmith.feature_context fc
SET win_rank = r.rank
FROM (
  SELECT fc_id, row_number() OVER (PARTITION BY feature_name ORDER BY priority, seg_ord) AS rank
  FROM flagsmith.feature_context
  WHERE snapshot_id = $1 AND seg_ord IS NOT NULL
) r
WHERE fc.fc_id = r.fc_id;

-- at evaluation: matched = the seg_ords this identity belongs to, computed once per identity
SELECT fc.*
FROM flagsmith.feature_context fc
WHERE fc.snapshot_id = $1 AND fc.feature_name = $2
  AND fc.seg_ord = ANY($3)        -- $3 = matched
ORDER BY fc.win_rank
LIMIT 1;                          -- no row → environment default
Each segment is evaluated once per identity, however many features it overrides. Flagsmith's current API forbids two overrides on one feature sharing a priority and treats the lowest number as the highest priority (updating flags), so ties only arise from synthetic segments.
Identity overrides. The SDKs express identity overrides as synthetic segments at priority −∞ with an IN condition on the identifier, and Flagsmith's Core API now does the same (issue #6654). pg_flagsmith keeps that model for the result but replaces the IN-list scan with one primary-key lookup in identity_override. The result is identical; the cost drops from a list scan to an index probe.
Overrides reach the environment document only when Environment Settings → SDK Settings → Use identity overrides in local evaluation is on (Edge Proxy docs). The live parity check flags a mismatch if it is off.
DEFAULT or STATIC. A feature falls back with DEFAULT when any segment, synthetic ones included, overrides it, and STATIC when none does. The loader stores that as a flag per feature.
Bucketing mode. Splits and variants hash the identity key. Local-evaluation SDKs and the engine derive it as <environment key>_<identifier>, which is pg_flagsmith's default. Not every Flagsmith path has always agreed: the Node SDK once used a database id instead, giving the same identity different variants across SDKs (issue #227). Callers can pass an explicit key, and the live parity check proves which convention your deployment uses.

Sync and atomicity
A load is one transaction: the whole new snapshot becomes current, or nothing changes. Readers can never see half a configuration, because Postgres hides uncommitted rows, and immutable snapshot rows mean a reader that has picked a snapshot id can never see a mix of two.
flagsmith.load_context(env_key, ctx json, source, source_rev, kind) runs these steps in one transaction:
1.  Serialise. pg_advisory_xact_lock(hashtextextended('flagsmith:' || env_key, 0)) allows one loader per environment; a second waits.
2.  Deduplicate. Hash the context with sha256. If it equals the current snapshot's hash, return the current id. Webhooks and polls can both fire safely.
3.  Normalise. Insert the snapshot, then its rows: segments through json_each(ctx -> 'segments') WITH ORDINALITY to keep their order, rules through a recursive CTE, conditions with their pre-parsed values, features, overrides with win_rank, variants with cumulative weights, identity overrides.
4.  Validate. Write warnings, then apply each environment's policies. A reject raises an error, the transaction rolls back, and the previous snapshot keeps serving.
5.  Compile (when enabled). Generate the SQL and run CREATE OR REPLACE FUNCTION. DDL is transactional in Postgres, so the new code becomes visible at the same commit as the new rows.
6.  Flip. UPDATE flagsmith.environment SET current_snapshot = <new id> for live loads; candidate snapshots are never pointed to.
7.  Collect garbage. Delete live snapshots beyond keep_snapshots that are also older than a grace period (10 minutes by default), and drop their compiled functions. The grace period protects long-running queries still reading them.
8.  Commit.

Sync sources
• Pusher (must ship). A small worker fetches the environment document from your self-hosted Flagsmith with a server-side key, maps it to an EvaluationContext with the official Python SDK's mapper, and calls load_context. Using the official mapper makes the mapping correct by construction. A Flagsmith webhook triggers it on every change; a 30-second poll backstops missed webhooks.
• In-database (stretch, Supabase). pg_cron schedules a request through pg_net, which is asynchronous, so a second job reads the response and loads it. This path needs a PL/pgSQL port of the mapper, checked against the mapper test cases in engine-test-data (PHP SDK PR). The server key lives in Supabase Vault.
Replicas and failure
• Physical replicas receive the rows, the pointer flip and the compiled functions in WAL order, so a load is atomic there too.
• Logical replication copies tables but not DDL. Run the loader on the subscriber, or set compile = false there.
• Flagsmith unreachable. Keep serving the last snapshot, as SDKs in local evaluation do, and report the staleness through flagsmith.health().
• Malformed document. The JSON cast fails, the transaction rolls back, nothing changes.
Performance
Postgres has no vectorised executor, so speed comes from four substitutes: evaluate whole populations in one statement, compile each snapshot into plain SQL the planner can see through, let the planner delete everything a query does not need, and spread large scans over parallel workers.

What the compiler generates. One UNION ALL arm per feature, each arm a CASE over its overrides in win_rank order, with every constant already parsed and every hash computed once inside an OFFSET 0 fence. A sketch of the shape for one multivariate feature:
CREATE FUNCTION flagsmith_c.flags_s42(identifier text, traits jsonb)
RETURNS SETOF flagsmith.flag_result
LANGUAGE sql STABLE PARALLEL SAFE AS $$
  SELECT 'search_ranking', true,
         CASE WHEN h.p <= 50 THEN '"boosted"'::jsonb ELSE '"control"'::jsonb END,
         CASE WHEN h.p <= 50 THEN 'boosted' ELSE 'control' END,
         CASE WHEN h.p <= 50 THEN 'SPLIT; weight=50' ELSE 'STATIC' END
  FROM (SELECT flagsmith.hash_pct(ARRAY['8812', 'k9Tz_' || identifier]) AS p
        OFFSET 0) h                      -- fence: one hash per call
  UNION ALL
  SELECT 'new_checkout', /* CASE over this feature's overrides */ …
$$;
A live snapshot is also published as flagsmith.flags(identifier, traits), recreated in the same load transaction.

Traps the compiler avoids
• Repeated expensive arguments. Inlining is refused when a costly argument is used more than once in the body, so callers pass columns, not expressions such as jsonb_build_object(…).
• No common-subexpression elimination. Postgres recomputes a repeated expression, so each hash is computed in a fenced subquery and referenced by name.
• Planning time. A snapshot with hundreds of segments generates large expressions. Measure planning time and fall back to the interpreter above a size threshold.
• Stale cached plans. After CREATE OR REPLACE, a prepared statement must serve the new snapshot. Prove it with a test: prepare, reload, execute, compare.
Benchmark plan. Use the profile Flagsmith uses for its own Edge Proxy: 50 features, 15 segments, every feature overridden by every segment (750 overrides), each segment matching on 15 trait conditions (Edge Proxy docs). Run it over 1M synthetic users and report:
• Point lookup latency, p50 and p99, for both tiers.
• Batch throughput in rows per second, for one feature and for all features.
• The official Python engine on the same data, as the baseline.
• Planning time for the compiled function.
Publish what you measure, with the script that produced it; set no target in advance.

1. The conformance suite, built first. Thursday morning, before any engine code:
• Pin engine-test-data to its latest tag; the SDKs and Flagsmith's SQL translator each pin a 3.x tag (SQL translator PR).
• Each test case holds a context and the result the reference produced (test data PR). For each one: load the context as a test snapshot, evaluate its identity, and compare the whole flags map and segments list, including variant and reason.
• Run against both tiers, in Supabase's Postgres image so the TLE install path is tested too.
• Report a pass count and an explicit expected-failure list with a reason per case, such as flag dependencies. Watching the count climb from zero is also good demo footage.
2. Differential fuzzing. Hypothesis generates random contexts: nested ALL, ANY and NONE rules, every operator, and values chosen for boundaries (thresholds 0, 50 and 100, negatives, 0.1, integers past 2⁶³, pre-release versions, Unicode and empty strings, JSON nulls). The official flag_engine.get_evaluation_result is the oracle. On a mismatch, Hypothesis shrinks the context to a minimal counterexample, which is saved in engine-test-data format as a new regression case and can be offered upstream.
3. Boundary tests written by hand
• Rehash path: brute-force an id pair whose digest reduces to 9,998 (1 in 9,999 inputs, found in seconds) and check it against Python.
• Exact split boundary: an identity hashing to exactly 50.0 under a 50% split.
• Cumulative weight equality, floor modulo on negative traits, a zero divisor.
• REGEX: anchoring, a leading inline flag, a trait containing a newline.
• SemVer: the specification's precedence chain.
• Collation: run the whole suite in a database created with a non-C locale, which proves every string comparison is pinned to byte order.
• Order: two equal-priority segments overriding one feature, loaded in both orders.
• Encoding: non-ASCII identifiers, so the hash runs over UTF-8 bytes.
4. Properties that must always hold
• Determinism: the same input gives the same output across sessions, servers and parallel workers.
• Tier equivalence: interpreter and compiled results are identical.
• Monotone splits: raising a split threshold never removes a member, a guarantee Flagsmith documents (operator docs).
• Idempotent loads: loading the same context twice returns the same snapshot id.
• Atomicity: a reader looping during 1,000 reloads never sees results from two snapshots in one call.
5. The live parity check. flagsmith-parity samples identities from your users table, evaluates each with the official SDK in local-evaluation mode against your self-hosted Flagsmith, evaluates the same identities in Postgres, and compares every flag. Mismatches report the identity and the differing field; results land in a parity_run table that flagsmith.health() reads.

• Loader and interpreter run as the owner. load_context and the PL/pgSQL interpreter are SECURITY DEFINER with SET search_path = pg_catalog, flagsmith, pg_temp. Neither is inlined, so the clauses cost nothing, and readers never need table access.
• Deny by default. The snapshot tables have row-level security on and no policies for application roles.
• Every constant is quoted. Rule values come from an external system, so the compiler writes every one through format('%L', …). A segment value such as '); DROP TABLE users; -- must compile into a harmless string literal; the fuzzer includes hostile strings to prove it.
• Compiled code is readable by every role. Inlining needs SECURITY INVOKER, and function bodies are visible to any role through pg_proc. So identity-override identifiers, which are often emails, stay out of compiled bodies and are looked up through a SECURITY DEFINER helper. Environments whose rule values are sensitive set compile = false.
• Secrets stay out of tables. The server-side environment key lives in the pusher's environment or in Supabase Vault, never in a table an application role can read.
Production readiness
The operating principle is "fail static": whatever goes wrong upstream, Postgres keeps serving the last good snapshot and says loudly how old it is.
Observability
• flagsmith.health() returns one row per environment: current snapshot, source revision, load time, age, open warnings, compiled or not, and the last parity result. Alert when age passes 5 minutes, when an error warning exists, or when parity reports any mismatch.
• Call counts come from pg_stat_user_functions with track_functions = 'pl'.
• Loader events are written with RAISE LOG in one structured line each: environment, snapshot, rows per table, compile time, warnings.

The pin is an emergency brake that works even when Flagsmith is down: one UPDATE restores the previous configuration for every query in the database. It diverges from Flagsmith until someone unpins, which is why health() reports it.
Limits. Flagsmith's defaults bound a snapshot: 500 segments per project, 2,000 segment overrides per environment, 100 rules per segment override and 1,000 bytes per rule value (operator docs). Demo 1: FlagShift, terraform plan for flag changes
flagsmith.plan() answers "who changes, and why?" for any proposed flag change, by evaluating the live and the proposed configuration over your real users in one SQL statement. A CLI and a GitHub Action wrap it. Open-source self-hosters get a review step they otherwise lack, since Change Requests and Release Pipelines are Enterprise features (data model).
The workflow
1.  Build the candidate. Either promote, by taking staging's context and re-keying it into production, or edit, by applying a JSON patch to production's live context. Load it with kind => 'candidate'; candidates are never served.
2.  Plan. SELECT * FROM flagsmith.plan('production', candidate => 77, population => 'app.users');
3.  Review. The CLI prints the plan; the GitHub Action posts it as a pull-request comment.
4.  Apply (optional). Write the change through Flagsmith's Admin API. The pusher syncs, and re-running the plan against the new live snapshot must show no changes. That empty diff is the verification.
5.  Revert with Flagsmith's version rollback, or flagsmith.pin in an emergency.
Re-keying is the insight. Bucketing hashes environment-specific keys: the identity key starts with the environment key, and the multivariate salt is a per-environment feature-state id. So "25% in staging" and "25% in production" select different people. If the two hashes are independent, only about a quarter of staging's cohort lands in production's, which is the expected overlap for any split p. A candidate therefore keeps production's environment key, feature keys and segment keys, and copies only rules, overrides, weights, enabled states and values. The plan reports the real overlap so nobody has to take the math on trust.
The core query
WITH pop AS (
  SELECT id::text AS identifier, traits FROM app.users
),
live AS (
  SELECT p.identifier, f.* FROM pop p,
         LATERAL flagsmith.get_flags(p.identifier, p.traits, snapshot_id => 42) f
),
cand AS (
  SELECT p.identifier, f.* FROM pop p,
         LATERAL flagsmith.get_flags(p.identifier, p.traits, snapshot_id => 77) f
)
SELECT feature,
       count(*)                                        AS users_changed,
       count(*) FILTER (WHERE NOT l.enabled AND c.enabled) AS turned_on,
       count(*) FILTER (WHERE l.enabled AND NOT c.enabled) AS turned_off,
       count(*) FILTER (WHERE l.variant IS DISTINCT FROM c.variant) AS variant_moves,
       (array_agg(identifier ORDER BY identifier))[1:5] AS sample_identities
FROM live l JOIN cand c USING (identifier, feature)
WHERE (l.enabled, l.value, l.variant) IS DISTINCT FROM (c.enabled, c.value, c.variant)
GROUP BY feature;
Reason transitions come from the same join, grouped by feature and the two reasons. When both snapshots are compiled, the same query runs against flags_s42 and flags_s77 and splits across parallel workers.

Demo 2: A/B testing a SQL ranking query
The ranking formula itself is the experiment. Postgres picks each user's arm with the same bucketing as the SDKs, ranks with that arm's formula in the same query, and Flagsmith Experimentation decides which ranking wins. No ranking code moves into the application.
Setup in self-hosted Flagsmith
Item
Configuration
Flag
search_ranking, multivariate: control (text relevance only) and boosted (relevance blended with 30-day sales), 50/50
Primary metric
search_result_clicked, occurrence, higher is better
Secondary metric
add_to_cart, occurrence, higher is better
Guardrail
search_latency_ms, mean, lower is better
The query
WITH v AS MATERIALIZED (       -- evaluated once per request, not once per product row
  SELECT flagsmith.variant('search_ranking', $1, $2) AS arm   -- $1 user id, $2 traits
)
SELECT p.id, p.title, v.arm
FROM products p, v, plainto_tsquery('english', $3) q          -- $3 search text
WHERE p.search_vec @@ q
ORDER BY CASE v.arm
           WHEN 'boosted' THEN ts_rank(p.search_vec, q) * (1 + ln(1 + p.sales_30d))
           ELSE ts_rank(p.search_vec, q)
         END DESC
LIMIT 20;
MATERIALIZED matters: without it Postgres may pull the CTE up into the outer query and call variant() once per candidate row.
Exposure and conversion. The query returns arm, so the application records the exposure with the SDK's track_exposure_event, then sends search_result_clicked with track_event when the user clicks; both exist in the Python SDK (PR #220). This is where parity becomes essential: if Postgres bucketed a user differently from Flagsmith, the exposure would be attributed to the wrong arm and the result would be noise. The conformance suite and the live parity check are what make this experiment valid.
Check before launching. Replay logged searches through both arms and measure how much the top ten differ. If the rankings barely differ, the experiment cannot detect anything and is not worth the traffic.
SELECT avg(cardinality(ARRAY(SELECT unnest(top_control) INTERSECT SELECT unnest(top_boosted))) / 10.0)
       AS mean_overlap_at_10
FROM search_log_replay;   -- one row per logged query, both arms' top ten as id arrays
Reading the result. Report the win probability with its credible interval, and say so when the interval still crosses zero, as the organisers' judging guide asks (How to Win Toggle Wars). Disclose that the demo traffic is simulated.
